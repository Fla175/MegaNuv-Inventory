# ADR-005: Script de geração ZIP com QR codes para todos os ativos-espaços físicos

| Campo | Valor |
|---|---|
| **Status** | proposta |
| **Data** | 30/10/2026 |
| **Deciders** | dono do projeto (MegaNuv) + arquiteto de software |
| **Origem** | Requerimento operacional: gerar download único de todos os QR codes dos ativos-espaces físicos em um arquivo .zip para facilitar impressão batch no local. |

---

## 1. Contexto

O sistema atual permite gerar QR code individualmente para cada ativo-físico ou espaço físico isolado através de `GET /api/qrcode/public-get`. No entanto, isso é **inviável para operações batch**:

- **Impraticável para impressão em lote**: Um operador precisa abrir, visualizar e imprimir separadamente dezenas/hcentenas de etiquetas para um evento, auditoria ou recontagem.
- **Sem controle de versão ou log**: Não há registro de quem gerou quais QR codes em que momento.
- **Sem limpeza automática**: Nenhum mecanismo limpa arquivos temporários após o download.
- **Não otimiza experiência**: O usuário navega entre múltiplas telas sem contexto de sessão.

Exige-se uma solução que ofereça:
1. Geração massiva de QR codes desde o banco de dados.
2. Compactação em ZIP único para download.
3. Botão acessível nas configurações.
4. Deletamento automático pós-download para segurança.

## 2. Decisão

### 2.1 Arquitetura da solução

```
┌─────────────────────────────────────────────────────────────┐
│                    Configurations Page                      │
│                     ┌─────────────────┐                     │
│                     │   Download      │                     │
│                     │    QR Codes     │   →   Modal         │
│                     │     Button      │          (confirm)  │
│                     └────────┬────────┘   →   Worker        │
│                              │   (background task)           │
│                              ↓                               │
│                 ┌─────────────────────────────┐             │
│                 │  pages/api/v1/qrcode-batch  │             │
│                 │    generate-zip.post        │             │
│                 └───────────┬─────────────────┘             │
│                             ↓                               │
│              ┌─────────────────────────────┐                │
│              │ lib/qrcodeGenerator.ts      │                │
│              │ - Query active.isPhysicalSpace = true       │
│              │ - Generate each QR code as PNG (500x500)    │
│              │ - Compress with jsZip         │
│              │ - Stream to response          │
│              │ - Return download URL temp    │                │
│              └────────────────┬─────────────┘                │
│                               ↓                               │
│              ┌─────────────────────────────────────┐          │
│              │  Auto-cleanup job (immediate)       │          │
│              │  Delete downloaded file by ID       │          │
│              └─────────────────────────────────────┘          │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 Componentes a ser desenvolvidos

#### Servidor (Next.js API Route)

1. **API Endpoint**: `POST /api/v1/qrcode-batch/generate-zip`
   - **Autenticação**: Required (`authMiddleware`)
   - **Corpo**: `{ format?: 'zip' }` (padrão zip)
   - **Resposta**: `{ success: true, downloadUrl: string, taskId: string }`
   - **Flow**: Worker gera QR codes → compacta em ZIP → serve download por ~30s → deleta arquivo

2. **Worker Engine**: `lib/qrcodeGenerator.ts`
   - Query todos ativos onde `isPhysicalSpace = true` (recursivo via children)
   - Para cada ativo:
     - Ler campos: `name`, `sku`, `manufacturer`, `model`, `serialNumber`, `tag`, `imageUrl`, `fileUrl`
     - Construir string de dados do QR code (ver §2.3 "Formato dos dados")
     - Renderizar como PNG (500x500px)
   - Usar `jszip` para compactar
   - Stream ZIP direto para resposta de Next.js (para evitar disco)

#### Frontend

1. **Componente Modal**: `components/settings/QRCodeBatchModal.tsx`
   - Campos: `format` (zip), `description`
   - Ação: `handleDownloadQRCodes`
   - Status: Loading/Success/Error com progress bar se possível
   - Feedback visual claro sobre progresso

2. **Integração em Settings**: Atualizar `/settings/components` para incluir botão "Baixar QR Codes em ZIP"

#### Segurança & Limpeza

1. **Temporário ZIP**: Arquivos criados no runtime são deletados imediatamente após o download (dentro de async function handler).
2. **ID do download**: Cada download gera UUID para rastrear/arquivar se necessário.
3. **Log de auditoria**: Registrar quem gerou, quando e quantos itens.
4. **Quota opcional**: Limitar número máximo de downloads/dia/seu usuário (future enhancement).

## 3. Opções Consideradas

### Opção A: Worker assíncrono com fila (Celery/BullMQ)

| Dimension | Assessment |
|-----------|------------|
| Complexity | Alta |
| Cost | Média (infra extra) |
| Scalability | Baixa para pequeno volume |
| Team familiarity | Baixa (nova infra) |

**Pros:** escalabilidade horizontal; não trava servidor.  
**Cons:** sobrecarga de infra; latência aditiva; complexidade de monitorar falhas.

### Opção B: Worker síncrono dentro do handler (escolhida)

| Dimension | Assessment |
|-----------|------------|
| Complexity | Média |
| Cost | Baixa (não há nova infra) |
| Scalability | Baixa para volumes > 5000 itens |
| Team familiarity | Alta (padrão existente) |

**Pros:** simples; feedback imediato ao usuário; zero infra extra; fácil debug.  
**Cons:** timeout maximo do Next.js (30–60s); CPU alta durante geração.

**Veredito:** O volume esperado (<5000 ativos fisicos totais) cabe em um worker síncrono. Adicionar queue seria overengineering inicial. Monitorar CPU e timeout futuramente.

### Opção C: Streaming PDF/A4 com QR codes

| Dimension | Assessment |
|-----------|------------|
| Complexity | Média |
| Cost | Baixa |
| Scalability | Alta |
| Team familiarity | Baixa |

**Pros:** print-friendly layout automático.  
**Cons:** biblioteca adicional necessária; menos flexible na formatação.

**Veredito:** QR code PNG é mais universal; layout pode ser controlado manualmente no modal se necessário. Manter simplicidade.

---

## 4. Análise de trade-off

A Opção B (worker síncrono com jsZip) foi escolhida porque:

- **Zero dependências externas** além de `jszip` já disponível no ecosystem;
- **Feedback imediato**: usuário vê status de progresso instantaneamente;
- **Simplicity**: fluxo linear, fácil de testar e manter;
- **Segurança**: arquivo criado e deletado no mesmo request, reduzindo surface area;
- **Custo de manutenção**: mínimo (um novo módulo + endpoint).

A Opção A (async/queue) foi rejeitada porque adicionaria complexidade desnecessária para um volume limitado. Se o sistema escalar para milhares de ativos, poderá ser revisitada.

A Opção C (PDF streaming) foi rejeitada para manter consistência com a abordagem image-based já usada no QR code view individual.

## 5. Consequências

### 5.1 Impactos positivos

- **Operações massivas simplificadas**: operador baixa um ZIP com todas as etiquetas e imprime no local.
- **Automação completa**: sem intervenção humana para organizar tags/batches.
- **Auditoria nativa**: quem baixou, quando e quais IDs estão no banco é rastreável via logs.
- **Economia de tempo**: redução de >90% no tempo para gerar/print batch (estimativa manual vs automatizada).

### 5.2 Impactos negativos

- **Uso de memória/CPU**: processamento síncrono consome recursos durante a geração; requer monitoramento para detectar gargalos futuros.
- **Timeout máximo**: se >5000 ativos fisicos existirem, o worker pode exceder 60s; fallback para resposta parcial ou alerta de espera futura.
- **Arquivo temporário**: ZIP criado no runtime não persiste para versionamento (delita imediatamente).

### 5.3 Riscos mitigados

- **Perda de arquivo**: deletação ocorre dentro do same request handler; fallback para salvar se timeout ocorrer.
- **Segurança**: apenas usuários autenticados podem acionar; nenhum dado sensível é exposto no payload.
- **Performance**: uso de `streamable` response evita I/O extra do disco durante compressão.

## 6. Design do formato do QR code

Cada QR code conterá a seguinte estrutura JSON compactada:

```json
{
  "type": "active",
  "id": "...",
  "isPhysicalSpace": true/false,
  "parentId": "...",
  "name": "...",
  "sku": "...",
  "manufacturer": "...",
  "model": "...",
  "serialNumber": "...",
  "tag": "...",
  "imageUrl": "..."
}
```

O texto será convertido para **UTF-8 bytes** antes de alimentar a biblioteca `qrcode.react` via `<Image />` (já usando base64).

Porquê este formato:
- Contém todo contexto técnico para identificar/atualizar depois.
- Inclui hierarquia via `parentId` e `isPhysicalSpace`.
- Mantém compatibilidade com leitores universais que leem UTF-8.
