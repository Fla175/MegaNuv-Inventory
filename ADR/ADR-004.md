# ADR-004: Modal de visualização de espaço-pai e ícone de expansão no ListSection

| Campo | Valor |
|---|---|
| **Status** | aceito |
| **Data** | 23/10/2026 |
| **Deciders** | dono do projeto (MegaNuv) + arquiteto de software |
| **Origem** | requisitos de front-end da Etapa C da ADR-003 — permitir interação com espaços-pai na página index (`ListSection.tsx`) e visualizar suas informações importantes (endereço, foto, responsável, telefone). |

---

## 1. Contexto

Na página index (`components/ListSection.tsx`), os espaços-pai são renderizados pelo componente `InventorySpaces`, que expõe apenas um menu de contexto (clique direito) e a árvore de ativos dentro de cada espaço. Não há como:

- abrir o card de um espaço-pai com clique esquerdo;
- ver as informações detalhadas do espaço (endereço, foto, nome do responsável, telefone);
- expandir/colapsar os ativos de um espaço-pai a partir de um ícone dedicado ao lado do nome.

O endpoint `GET /api/father-spaces/list` já retorna todos os campos do banco (incluindo `address`, `responsible`, `phone`, `imageUrl`), mas o type `FatherSpace` em `types/inventory.ts` não os expõe e não existe endpoint de detalhes por id.

---

## 2. Decisão

Adicionar ao `ListSection`:

1. **Novo endpoint** `GET /api/father-spaces/[id]` que retorna o `FatherSpace` completo pelo id (incluindo `address`, `responsible`, `phone`, `imageUrl`). Retorna `404` quando não existe e exige sessão autenticada (`401` sem sessão).
2. **Componente `SpaceDetailModal`** dedicado (`components/list/SpaceDetailModal.tsx`), somente leitura, espelhando o comportamento de `ItemDetailModal` dos ativos (abre/fecha com `Esc` e botão X). Exibe foto, nome, endereço, responsável e telefone; campos vazios mostram texto descritivo.
3. **Mecânica de interação** no card do espaço-pai (design corrigido após grilling):
   - **Clique no card inteiro** (exceto o ícone `map-pin`) → abre o `SpaceDetailModal`; o `map-pin` é o único trigger de toggle de expansão/colapso (sem chevron adicional).
   - `onContextMenu` no cabeçalho do espaço-pai **não renderiza** o contexto do espaço — a trava original (arquitetura) restringe o contexto aos ativos (`ActiveTree`); o modal de detalhes substitui ações de espaço.
   - Em modo de seleção (`isSelectionMode`), o clique no card é desativado para não sobrepor a árvore.
4. **Permissão:** qualquer usuário autenticado vê o modal (readonly). Somente `DIRECTOR` e `ADMIN` veem um botão de edição dentro do modal, que dispara o handler de edição de espaço (`onEditSpace`) sem fechar o modal automaticamente.
5. **Estado** em `ListSection`: `selectedSpace` (espelho de `selectedViewItem`), `handleSpaceClick` (fetch do endpoint + seta estado), `handleSpaceToggleExpand` (toggle de expansão), e `useEscapeKey` para fechar com `Esc`.

---

## 3. Opções consideradas

### Opção A: estender o type `FatherSpace` e usar o array já passado

| Dimension | Assessment |
|-----------|------------|
| Complexity | Baixa |
| Cost | Baixa (sem novo endpoint) |
| Scalability | Média (carrega todos os campos de todos os espaços sempre) |
| Team familiarity | Alta |

**Pros:** sem novo endpoint; dados já estão no `fatherSpaces` passado como prop.

**Cons:** o type `FatherSpace` não expõe `address`/`responsible`/`phone`/`imageUrl` (força `any` ou cast); não é RESTful para um recurso único; tudo é carregado de uma vez.

### Opção B: novo endpoint `GET /api/father-spaces/[id]` (escolhida)

| Dimension | Assessment |
|-----------|------------|
| Complexity | Média |
| Cost | Média (novo endpoint + teste de API) |
| Scalability | Alta (carrega só o espaço necessário) |
| Team familiarity | Alta (segue padrão dos outros `[id].ts`) |

**Pros:** dados tipados e sob demanda; endpoint consistente com o restante da API; tipo dedicado no frontend.

**Cons:** exige novo arquivo de rota e novo teste de API.

### Opção C: reutilizar `SpaceModal` (edição) disfarçado de visualização

| Dimension | Assessment |
|-----------|------------|
| Complexity | Baixa |
| Cost | Baixa (sem novo componente) |
| Scalability | Baixa (acopla visualização a edição) |
| Team familiarity | Média |

**Pros:** reaproveita o formulário existente.

**Cons:** mistura responsabilidades (edição vs visualização); campos desabilitados são UX confusa; não segue o padrão de `ItemDetailModal` (readonly dedicado).

---

## 4. Análise de trade-off

A Opção B foi escolhida porque:

- preserva a separação de preocupações (visualização × edição) já estabelecida entre `ItemDetailModal` e os modais de edição;
- não força `any` ou casts no type `FatherSpace`;
- segue o padrão existente de rotas dinâmicas `[id].ts` na API;
- o custo adicional (novo endpoint + teste) é justificado pela tipagem segura e pelo carregamento sob demanda.

A Opção C foi rejeitada porque acopla visualização a edição e polui o `SpaceModal` com estados de somente leitura. A Opção A foi rejeitada porque o type não expõe os campos necessários e acarretaria casts inseguros.

---

## 5. Consequências

- **Fica mais fácil:** visualizar dados do espaço-pai sem sair da lista; expandir/colapsar ativos por ícone dedicado; consistência com o comportamento dos ativos (`ItemDetailModal`).
- **Fica mais difícil:** manutenção de um novo endpoint e de um novo componente modal (superfície de código maior).
- **Precisa ser revisitado:** se futuramente a edição de espaço-pai for movida para fora de `/settings`, o `onEditSpace` passado ao `SpaceDetailModal` precisará ser reavaliado.
