# ADR-006 — MinIO Access for Image Visualization

| **Status** | proposta |
| **Data** | 04/11/2026 |
| **Deciders** | equipe de desenvolvimento |
| **Origem** | análise de acesso MinIO para visualização de imagens; crédito às credenciais e políticas existentes em `lib/minio.ts`, `inventory-policy.json`, `inventory-policy-auditor.json` e `scripts/audit-minio.ts` |

## 1. Contexto

O sistema armazena imagens e arquivos no MinIO bucket `inventory`. Para visualização dessas imagens na UI, dois fluxos principais são utilizados:

1. **Endpoint `/api/storage/file`** (`pages/api/storage/file.ts`): busca o objeto diretamente do MinIO usando `minioClient.getObject()` e serve ao navegador com headers apropriados para visualização inline.

2. **Endpoint `/api/qrcode/public-get`** (`pages/api/qrcode/public-get.ts`): gera URLs assinadas (presigned URLs) usando `minioPublicClient.presignedGetObject()` para disponibilizar imagens no frontend.

Ambos os fluxos utilizam as **credenciais da aplicação** (`MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY`) e a política `inventory-policy.json`, que concede:

- `s3:GetObject` — bucket `inventory` e `inventory/*`
- `s3:PutObject` — bucket `inventory` e `inventory/*`
- `s3:DeleteObject` — bucket `inventory` e `inventory/*`

A política de auditoria `inventory-policy-auditor.json` concede adicionalmente:

- `s3:ListBucket` — bucket `inventory` (necessário para enumerar objetos)
- `s3:DeleteObject` — bucket `inventory/*`

## 2. Problema Identificado

O projeto não consegue chamar nenhuma imagem do MinIO para visualização. A análise revelou dois possíveis cenários:

### 2.1 Uso incorreto de credenciais ou políticas

Embora a política `inventory-policy.json` conceda `s3:GetObject` (necessário para `getObject` e `presignedGetObject`), pode haver uma discrepância entre o que a política declara e o que o servidor MinIO tem realmente aplicado. O script `scripts/audit-minio.ts` deixa claro que:

> "a credencial da aplicação **não tem** `ListBucket` — `inventory-policy.json` concede apenas `GetObject`/`PutObject`/`DeleteObject`"

Se o MinIO server tiver políticas mais restritivas ou se as credenciais não foram criadas com as permissões corretas, as operações de leitura falharão com `AccessDenied`.

### 2.2 Credenciais de auditoria sendo usadas indevidamente

O `scripts/audit-minio.ts` foi desenhado para usar credenciais separadas (`MINIO_AUDIT_ACCESS_KEY`/`MINIO_AUDIT_SECRET_KEY`) com a política `inventory-policy-auditor.json` quando é necessária a operação de listagem (`ListBucket`). Porém, a aplicação atual (`lib/minio.ts`, `pages/api/storage/file.ts`, `pages/api/qrcode/public-get.ts`) **sempre usa as credenciais da aplicação**, não as do auditor.

Isso pode ser adequado para visualização pura (que só precisa de `GetObject`), mas se houver alguma operação intermediária que implicitamente requira listagem ou outras permissões, o uso das credenciais erradas causaria falhas.

## 3. Decisão

Como ação inicial para o ADR-006, recomenda-se o seguinte:

1. **Validar as credenciais e políticas no MinIO server** — confirmar se as credenciais `MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` têm realmente `GetObject` aplicado no bucket `inventory`, e se o bucket tem a policy attached.

2. **Se as credenciais da aplicação falharem**, migrar o uso de `minioPublicClient` (para `presignedGetObject` no QR code) e `minioClient` (para `getObject` no storage/file) para usar as **credenciais de auditoria** `MINIO_AUDIT_ACCESS_KEY`/`MINIO_AUDIT_SECRET_KEY`, que têm as políticas completas incluindo `ListBucket`.

3. **Se as credenciais da aplicação já funcionarem**, documentar o motivo pelo qual funcionam e garantir que não haja regressão — manter o status quo, mas adicionar testes de integração que validem a visualização de imagens.

4. **Criar um helper único** para selecionar a credencial correta dependendo do contexto (visualização vs auditoria), evitando a duplicação de lógica de cliente MinIO em vários arquivos.

## 4. Items de ação para ADR-006

- [ ] **Testar acesso a imagens**: tentar acessar uma imagem conhecida através de `/api/storage/file?key=<key>` e `/api/qrcode/public-get?id=<id>` para identificar o erro exato (403, 404, connection refused, etc.).

- [ ] **Verificar política no MinIO**: usar a CLI do MinIO (`mc policy download/list/attach`) para confirmar se `inventory-policy.json` está attached ao bucket `inventory` e se as credências têm as permissões esperadas.

- [ ] **Testar com credenciais de auditoria**: temporariamente configurar `MINIO_AUDIT_ACCESS_KEY` e `MINIO_AUDIT_SECRET_KEY` no .env e verificar se as operações de visualização funcionam (isso confirmaria se o problema é na política da aplicação).

- [ ] **Definir credencial padrão para visualização**: decidir se a aplicação deve usar sempre credenciais da aplicação ou do auditor para operações de leitura/visualização, e criar um helper em `lib/minio.ts` para encapsular essa decisão.

- [ ] **Atualizar documentação**: caso a decisão mude o uso de credenciais, atualizar `CONTEXT.md`, `SPECS.md` e o `CHANGELOG.md` accordingly.

- [ ] **Implementar o helper**: se houver mudança de credencial, refatorar `lib/minio.ts` para expor uma função `getMinioClient(mode: 'app' | 'auditor')` que retorne o cliente adequado, em vez de ter dois clientes fixos com credenciais diferentes.

## 5. Relação com outras ADRs

- Esta ADR depende do diagnóstico correto das permissões MinIO. Se for constatado que a política `inventory-policy.json` está incompleta, ela pode influenciar a revisão da matriz RBAC em `ADR-002` e `SPECS.md §4.2`.
- O helper de seleção de credencial pode ser compartilhado com o `scripts/audit-minio.ts` para evitar duplicação de lógica de cliente.
